11.2 Changes on 05.10.2026

  1. Added the v6 NGS Excel sample-sheet template to the main project view and new-project dialog with matching green download buttons.
  2. Added optional .xlsx upload and validation for the project_metadata sheet. SampleName, SampleType, and Volume are required; Description_Condition (optional) and Concentration (optional) may be empty; ProjectNumber must remain blank; and facility-generated SampleIndex/DataName values may not be replaced.
  3. Added an administrator setting that switches future project submissions between optional and mandatory sample-sheet upload without redeployment.
  4. After project creation, finalized valid uploaded workbooks by filling the assigned P#### into ProjectNumber for every validated sample row and renaming project_metadata to P####. The finalized workbook is attached to the project-creation email and stored under P####_<LDAP username> in /fs/pool/pool-ngs-public.
  5. Added persistent local fallback storage at /srv/ngs-app-data/uploads_pending_pool, detailed failure alerts to omicsdesk@biochem.mpg.de, and database metadata/checksums for each upload.
  6. Prepared deployment for ngs-shiny-user:b_ngs, including fallback ownership, dependency checks, mount verification, and updated operational documentation. The service account does not need the legacy shiny group.
  7. Added a deployment preflight that checks all required R packages as the actual ngs-shiny-user worker before application files are synchronized or Shiny Server is restarted.
  8. Changed LDAP smoke-test credential handling from an unquoted .netrc entry to a protected curl configuration file so passwords containing spaces, quotes, or backslashes are preserved correctly.
  9. Added a pre-restart SQLite gate that repairs database sidecar ownership and verifies both the application directory and production database as ngs-shiny-user. Deployment now stops if the database is absent or cannot be opened.
  10. Fixed the production-database existence guard to run with elevated access after the app directory is restricted to 0750; deployment users outside b_ngs no longer receive a false “database not found” result.
  11. Added a login-shell traversal preflight matching Shiny Server’s launch behavior, so deployment stops with a path-permission diagnostic when the runtime account cannot enter the deployed application directory.
  12. Added zip/unzip deployment requirements for lossless finalization of submitted .xlsx workbooks without another R package dependency.

11.3 Changes on 04.10.2026

  1. Added durable project-status history in the new project_status_history table:
    • stores the internal project row ID, status, change timestamp, and responsible username
    • indexes history by project, timestamp, and history-row ID
    • deletes associated history when a project is deleted.
  2. Added an idempotent migration for existing projects:
    • creates exactly one baseline history row where none exists
    • uses the project’s current status and updated_at, falling back to created_at
    • identifies the source as migration
    • the baseline date is approximate because earlier status transitions were not recorded historically.
  3. Added transactional history recording to every supported status-change path:
    • newly created projects receive an initial Created entry
    • Edit Project and the separate Update Project Status dialog add a row only when the status genuinely changes
    • project creation/status changes and their corresponding history entries now succeed or roll back together
    • saving without changing the status does not create duplicate history.
  4. Added a visible status history directly below Project Status in Edit Project:
    • administrators retain the editable status dropdown
    • regular users see a read-only current-status badge
    • all users see completed statuses oldest-to-newest with a YYYY-MM-DD date
    • the current status is excluded from the completed-status list.
  5. Applied the BCFMS status palette to the Edit Project status display only. Existing project-table status colors remain unchanged.
  6. Preserved the existing Data released notification and immutable cost-snapshot behavior while making the status and cost-lock update part of the same transaction.
  7. Validated the change against disposable databases:
    • a copied production backup created 953 baseline rows for 953 projects and did not duplicate them on reconnect
    • a clean database setup created one baseline row for each sample project
    • new-project creation, both status-change interfaces, unchanged-status saves, history ordering/current-status exclusion, deletion cleanup, administrator and regular-user displays, and all status colors were verified
    • a forced history-write failure confirmed that the project status update is rolled back.

11.4 Changes on 17.09.2026

  1. Added an administrator-only Unlock Costs action to the Edit Project window for projects with locked cost snapshots.
  2. Unlocking requires a written reason and records a durable audit entry in project_cost_unlock_log, including:
    • project and previous snapshot identifiers
    • previous locked total
    • administrator username
    • unlock reason and timestamp
    • subsequent relock username and timestamp.
  3. Added a safe correction workflow for Data released projects:
    • unlocking removes the active snapshot but retains its amount in the audit log
    • the project remains deliberately unlocked across database connections and app restarts
    • the administrator table displays Unlocked · Admin override
    • Edit Project displays the administrator, time, and reason for the override
    • saving the corrected Data released project calculates its current total, creates a new immutable snapshot, and closes the audit entry as relocked.
  4. Updated project deletion and fresh-database setup to include the new unlock audit table.
  5. Validated the complete locked → unlocked → persistent override → relocked lifecycle against a temporary copy of the September production backup.

  1. Audited the NGS project cost calculation against the latest production database backup and the BCFMS implementation:

    • added warnings when a selected option requires an administrator-entered additional cost or references missing lookup data.

    • total cost.

    • editable by administrators and read-only for regular users

  4. Seeded the initial Maschine / Cycles choices:
    • 2×60bp NovaSeq
    • 2× 75bp Aviti
    • 2× 75bp PE-Seq
    • 45bp SE-seq - CRISPR.
  5. Added Maschine / Cycles Management to the Administrator Panel:
    • choices are now stored in machine_cycles_options instead of only being hard-coded
    • administrators can add or archive dropdown options
    • archiving an option does not erase the text already stored on existing projects.
  6. Added a data-preserving migration for the four legacy machine/read-length entries:
    • their values are copied into projects.machine_cycles
    • projects are reassigned to the generic up-to-150-cycle pricing entry when the legacy cycle option is archived
    • historical machine/cycle information and the existing cost category are preserved.
  7. Added database-level reference-integrity guards for all project lookup menus:
    • referenced users, budget holders, sample types, sample service types, sequencing depths, sequencing cycles, reference genomes, and sequencing platforms cannot be deleted
    • referenced text-based reference genomes and sequencing platforms cannot be renamed without migrating project values first
    • failed deletion attempts now show a user-facing error and leave existing projects unchanged.
  8. Improved handling of previously broken lookup references:
    • projects remain visible through LEFT JOIN queries even when an old lookup row is missing
    • project tables and edit dialogs show explicit labels such as [Missing depth ID …]
    • missing selections are preserved in Edit Project instead of silently switching to the first available option.
  9. Audited both database backups for historical lookup loss:
    • the September backup contains 953 projects, of which 857 have at least one missing numeric lookup reference
    • 846 of the affected projects are marked Legacy project; 11 are non-legacy projects
    • the April backup already contains almost the same missing references, so most deleted labels cannot be reconstructed reliably from that backup
    • only a small number of budget-holder and sequencing-depth labels have exact recoverable ID matches; no automatic merge was performed.
  10. Simplified local development startup:
    • mailR/rJava and ldapr are optional only when APP_ENV=dev and AUTH_MODE=local
    • local UI testing can run without Java, email delivery, or LDAP
    • production and LDAP modes still require those dependencies.
  11. Enabled automatic biweekly database backups:
    • uses SQLite’s online backup API for a consistent live snapshot
    • creates at most one backup per two-week ISO calendar period
    • records successful automatic backups in backup_logs
    • defaults to /srv/shiny-server/DB_backup
    • supports an override through DB_BACKUP_DIR.
  12. Updated setup_database.R for fresh installations with the new project column, explicit cycle pricing, Maschine / Cycles option table and defaults, and foreign-key enforcement.
  13. Validated the changes with R parse checks, whitespace checks, temporary copies of the production backup, cost-resolution tests, deletion/migration tests, database-trigger tests, full admin project loading, and an automatic-backup integrity check.
  14. Replaced destructive deletion with archive/reactivate handling for all project lookup menus:
  • users
  • budget holders
  • sample service types
  • sequencing depths
  • read lengths/cycles
  • Maschine / Cycles options
  • reference genomes
  • sample types
  • sequencing platforms
  • archived entries are hidden from active admin tables and new-project dropdowns, but remain attached to existing projects and retain their historical prices
  • existing projects show an archived label instead of silently switching to another menu entry.
  1. Added an Archived Entries area to the Administrator Panel:
  • archived rows are separated by category to keep active management lists clean
  • administrators can inspect who archived an entry and when
  • a selected entry can be reactivated without recreating it or changing project references
  • archived users can no longer log in; the current administrator and the last active administrator cannot be archived.
  1. Added immutable cost snapshots for projects whose status is Data released:
  • the stored projects.total_cost is copied to project_cost_snapshots.locked_total
  • later changes to prices, labels, or archived lookup entries do not alter the locked amount
  • cost-driving fields are read-only in Edit Project once a snapshot exists
  • changing an existing project to Data released creates the snapshot in the same update flow.
  1. Backfilled and audited the 84 existing Data released projects from the September backup:
  • all 84 receive a locked snapshot
  • 64 have complete lookup data and match the current formula
  • 13 have complete lookup data but a stored total that differs from the current formula
  • 7 have incomplete historical lookup data
  • the 20 projects in the last two groups are flagged for administrator review, while their stored totals remain unchanged.
  1. Added cost-review indicators in the requested administrator locations:
  • a Cost Review list in the Administrator Panel
  • a Cost Status column and filter in the administrator project table
  • a warning banner and locked cost breakdown in Edit Project
  • administrators can record a review note and mark a flag reviewed without recalculating the locked total.
  1. Re-tested the migration against a temporary copy of the September production backup, including all 84 snapshots, the 20 review flags, archive/reactivate behavior, preservation of archived pricing, database deletion guards, and locked-total stability after a price change.

11.17.1 VM rollout validation (what I tested and confirmed)

I verified end‑to‑end behavior on the VM after fixing the Apache proxy path:

  • LDAP login works: the browser prompts for username/password and redirects to /sequencing-app/?auth_user=<user>.
  • User mapping works: exampleuser (OU contains Cox) is mapped to the Cox group and the correct PI.
  • User mapping works: exampleuser-test (OU = NGS Facility) is treated as a service‑group user (no PI match).
  • Email routing works: research group users trigger mail to the PI and NGS.
